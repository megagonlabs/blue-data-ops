# Changelog

Notable changes per release, newest first.

This repository publishes three distributions and versions each independently, so an entry names which of them moved and what a caller of that one has to do.
The rules are in [design/12-deployment-ops.md](design/12-deployment-ops.md#1-versioning); an operator card's own `@MAJOR.MINOR.PATCH` is a fourth axis and moves with neither.

## blue-data-ops 1.0.0, blue-data-ops-mcp 1.0.0, blue-data-ops-cli 1.0.0 — pre-release

This release adds the `blue-ops` command, renames the MCP tool surface, publishes the schema constraints already enforced by the library, and restricts provider routing and limits discovery results to identifiers.
MCP clients must use the new tool names. Clients that validate against the published schema may also need to supply newly declared required attributes.
The release label is 1.0.0 for all three distributions. Operator and schema versions retain their own identities; the API and migration notes below still apply.

- HTTP now defaults to `127.0.0.1:8010`, with shared API-key and CSRF guards on streamable HTTP and SSE. Existing clients must configure `BLUE_DATA_OPS_MCP_KEY` and send `X-API-Key` or Bearer authentication. Deliberate no-key HTTP requires `BLUE_DATA_OPS_MCP_AUTH_DISABLED=true`.
- The dependency floor is blue-data 1.0.0; MCP requires its `server` extra. Python 3.12 is recommended and release checks target 3.11 and 3.12.
- The checkout includes the three CLI JSON examples, the Code of Conduct, disclosures, dataset and OSS inventories, and matching NOTICE files.

**Added**

- Add a regular CPython 3.15 installation route on macOS ARM64 with hash-verified LiteLLM/fastuuid compatibility wheels and explicit constraints.

- LLM-backed operators accept the provider-neutral `llm.reasoning_effort` call property. The CLI
  exposes it as `--reasoning-effort` for individual operator and stored-pipeline runs, and the
  library, CLI, and MCP guides show model and effort selection for `nl2llm` and `semantic_filter`.
  Omission sends no effort setting. A higher-precedence layer may use `null` to clear an inherited
  value.
- **A command line, `blue-ops`, in a new distribution `blue-data-ops-cli`.** 24 commands over `profile`, `catalog`, `operator`, `pipeline` and `metadata`, with `operator resource` under `operator`, in the `<cli> <component> <action>` shape the rest of the Blue family uses. It runs an operator over a record bundle, searches and inspects the catalog, exports an operator's resource package, and plans, stores, inspects and runs pipelines. A record bundle arrives as a file or on standard input rather than as an argument, because `list[list[dict]]` does not survive argv. `--format table|json|nl` is on every command that returns a result, settings resolve through command option → environment variable → profile → built-in default, and ten exit codes carry the library's own failure families. [`docs/cli.md`](docs/cli.md) is the reference; [`platform/ops-cli/README.md`](platform/ops-cli/README.md) is its source of truth.
- **The MCP adapter installs a console command.** `blue-data-ops-mcp` replaces `python -c 'from blue_data_ops_mcp import serve; serve()'`, and `blue_data_ops_mcp.main` is the function behind it. The old Python call still works.
- **A `LICENSE` at the repository root**, covering all three distributions. There was none. It is a BSD 3-Clause licence with a fourth attribution and NOTICE clause.
- **`build.sh`, `install.sh` and `publish.sh` under each package's `scripts/`.** Build scripts run `python -m build` and then check the wheel's package files against `src/`. All three build scripts first remove their own `build/` and `dist/`, and their checker refuses any package member `src/` does not declare, whatever its suffix, as well as duplicate archive entries. Install scripts resolve the sibling `blue-data` checkout. Publish scripts require an explicit destination, select the one wheel and source distribution for the current version, check that wheel's package files, run `twine check`, and upload only those two artifacts.
- **This changelog, and `docs/cli.md`.** Release history previously lived only in the migration sections of the package READMEs.

**Changed**

- OpenAI calls retry once without temperature when the provider rejects an inherited operator
  default. Explicit caller and client temperatures remain strict. Clients built by copying
  operator defaults must remove or clear the copied temperature when omission is intended;
  use `llm.temperature=null` in JSON or `None` in Python.

- Execution diagnostics distinguish malformed model replies, supported loaded database/provider
  failures and provably absent local SQLite generation targets. Host SQL capability guards remain intact; remote target checks remain limited.
- Retained and default v1/v2 semantic operators reject malformed replies rather than coercing them to empty success. Valid negative and empty replies remain valid, and active semantic v3 behavior is unchanged. Retained `semantic_filter` accepts booleans and trimmed, case-insensitive string pairs `true`/`false`, `yes`/`no`, `1`/`0` and `include`/`exclude`. Legacy join accepts complete pair objects with booleans or the strings `true`, `yes`, `1`, `match` and `join` for a match and `false`, `no`, `0` and `exclude` for no match; `include` is rejected. Active v3 join still requires native booleans. See [compatibility](lib/COMPATIBILITY.md#legacy-semantic-response-handling) for the accepted reply formats.
- NL2BN preserves typed provider errors when no correction runs, clears old error provenance after a successful client response, and uses fixed format/service feedback for corrections.
- `OperatorExecutionError` lets trusted custom authors publish bounded fixed diagnostic constants.
  Retryability is caller advice, with no added retries or write-replay guarantee.
- Pipeline CLI summaries use the stopped node's recoverable record. MCP contains exceptions escaping
  custom `run()` overrides with the same generic metadata as PipelineExecutor, preserving cancellation
  and deadline behavior.

- LLM operator failures now return safe, specific messages and suggestions for configuration and provider failures. CLI JSON output remains one JSON object when LiteLLM reports a failure.
- Local `bad_override` and `reserved_field` configuration refusals are non-retryable and make no provider request. The code distinguishes forbidden `llm.*` overrides from forbidden service-prefixed properties.
- CLI operator and pipeline execution suppresses root and existing Blue library diagnostic logs by default and masks them on standard error with `--log`. Shared attribute-validation failure logs omit exception text.
- `PipelinePlanner` disambiguates compiled step labels against the request's `input_label` and `output_label` and earlier step labels. Requests with identical nonempty endpoint labels now fail with `INVALID_REQUEST`.
- **LLM pipeline controls resolve node, stored pipeline, invocation, then operator default.**
  This order covers the model-generation aliases, including model and reasoning effort. Other
  execution properties keep their existing node, invocation, stored-pipeline order, so a stored
  pipeline cannot replace an invocation-supplied `execution.timeout_seconds` or `data_registry`.
  **Migration:** move an LLM value that must vary per execution out of the stored pipeline, or set
  it on the individual node when that node must differ from the rest of the pipeline.
- A provider rejection with structured error code `unsupported_parameter` is non-retryable and is
  returned as a contained operator error without provider details. Other provider failures keep the
  existing retry policy.
- **Breaking: every MCP tool is renamed.** The 33 names gain an `ops_` prefix, so `select` becomes `ops_select` and `create_database` becomes `ops_create_database`. **Every existing client call site changes.** A client holds one flat tool namespace across the servers it has loaded, and this family ships a server per source: `create_database` was already served with a different meaning by `blue-data-user-source`, and both are writes. Nothing else about a tool moves — `_meta.operator_id` still carries the unprefixed logical name, the three arguments are the same containers, and the result envelope is unchanged. **Migration:** prefix the tool name at each call site. A client that reads its tool list from `list_tools()` rather than hardcoding names needs no change beyond a fresh listing.
- **The published MCP input schema now says what core already enforced, which is a contract break rather than a behaviour break.** Each attribute carries its JSON Schema `type`, an attribute core declares required appears in the `attributes` object's `required` list — 46 of them, across 27 tools — and 17 attributes whose values core's validator closes carry an `enum`. The three top-level arguments each carry a description. **The server's own behaviour is unchanged**: it does not validate against the published schema, so a call that omits a required attribute still reaches operator validation and comes back as a recoverable `INVALID_INPUT` record with `isError` false, exactly as before. What changes is what a *client* does with it: a client that validates arguments against the advertised schema will now refuse a call it used to send, and the server would still have answered. **Migration:** a caller that was relying on the schema's permissiveness to send a partial `attributes` object gets a client-side refusal; send the required attributes, or stop validating locally and read the error record the server returns.
- **Breaking: the provider is the deployment's, not the caller's.** A model name is a routing instruction to the provider library — `vertex_ai/gemini-2.5-pro` selects Vertex, and so does a bare `gemini-2.5-pro` — so a caller who could set `openai.model` could choose which provider spent this deployment's credentials. Dispatch now comes from the environment the process starts in, which is the one channel a tool caller cannot reach. `BLUE_DATA_LLM_PROVIDER` names the provider on every call and defaults to `openai`; it is checked against the provider library's own name list before each LLM-backed call, and a name the library does not serve is refused with `bad_provider`, naming the variable and the value. Where that library will not enumerate its providers there is nothing to check against and the call proceeds. `BLUE_DATA_LLM_ALLOWED_MODELS`, when set, is the exact model set a property may ask for, and it only ever narrows. A model that would dispatch elsewhere is refused with `model_not_allowed`, checked both on the outcome the provider library would produce and on the spelling, because neither check covers the other. A slash is not itself a provider prefix: `accounts/fireworks/models/llama-v3` names a model and is accepted without listing. **Migration:** a deployment reaching any provider other than OpenAI through the model string must set `BLUE_DATA_LLM_PROVIDER`. Until now the provider was inferred from the model name, so this worked by accident.
- **Breaking: provider-call properties are now restricted to generation settings.** Before this release, a `properties` entry naming any LiteLLM field — `api_key`, `api_base`, `base_url`, `custom_llm_provider`, `extra_headers`, the Vertex and Bedrock project, tenant and region selectors, and the rest — was merged into the provider call and forwarded. The namespace now admits the generation parameters of the call and refuses everything else, so which provider answers, at which endpoint, in which project, tenant or region, and under which credential are the deployment's to set and not a caller's. On the MCP adapter `properties` is a tool argument, so **any caller that could reach a tool could send that server's prompt to an endpoint of their choosing, authenticated with a key of their choosing, and the deployment had no sign of it**. Nothing in this repository ever documented that route; the endpoint and the credential come from the environment the server process starts in. Such a service-prefixed property now raises `LLMError` with code `reserved_field` (a forbidden `llm.*` override uses `bad_override`), naming the fields it refused, before the cache key is built — so nothing sent under one of those names is written to the response cache either. A census of forbidden names would be right only until the provider library's next release, so the rule is the other way round: the namespace admits a closed set of generation parameters, derived from that library's own call signature and supported keyword surface, and refuses everything outside it. **Migration:** put the key and the endpoint in the environment the server or the process starts in. A deployment that discovered `openai.api_key` worked will now get an error result instead of an answer.
- **Breaking: caller-supplied mock responses are now rejected.** LiteLLM returns `mock_response` verbatim without calling anyone, so a `properties` entry setting it made a tool hand back text the caller wrote, presented as a model's answer. Over MCP the caller is usually one agent and the reader of the answer another, which makes that an integrity problem regardless of how far it travels. Service-prefixed `mock_response` and `mock_timeout` now raise `LLMError` with code `reserved_field` and their own message; the `llm.*` equivalents use `bad_override`. **Migration:** inject a client through `properties["llm_client"]` to serve canned responses in a test, which is the seam that exists for it.
- **Breaking: callers can no longer set operator prompt, extraction or transport controls.** `input_template`, `input_json`, `input_context`, `input_context_field`, `input_field`, `output_template`, `output_path`, `output_transformations`, `output_strip`, `output_cast`, `template_syntax`, `service_prefix`, `openai.api` and `openai.service_url` in call properties are refused with `reserved_field`, even when the value is `null`. An unknown `llm.*` setting is refused with `bad_override`. **Migration:** define custom prompts and extraction in trusted operator defaults, and send only documented `llm.*` and generation settings. See [the security changes](lib/COMPATIBILITY.md#llm-prompt-and-sql-execution-security-changes).
- **Breaking: prompts render in one pass.** `utils.safe_substitute` keeps its import and signature but applies one `$`-placeholder pass, and operator prompts render the same way. Unknown names, inserted `$` tokens and Jinja syntax stay literal; chained and Jinja evaluation from Blue's older helper is gone. **Migration:** put every value a prompt needs into the substitution call directly.
- **Breaking: `nl2sql` generates SQL and does not run it, in every retained version.** Running the query needs a host-bound `ReadOnlySQLExecutor`, an exact approved target and `execute_query=True`. The stock CLI and MCP instances have no executor, and caller registry selectors cannot grant or redirect execution. **Migration:** run the returned SQL yourself, or configure an executor in a host-built operator; see [SQL execution](docs/llm-settings.md#sql-execution).
- **Breaking: MCP registry tools use the server's one deployment registry.** Caller `data_registry`, `platform.name` and `data_registry.name` cannot select it, and a server with no registry configured returns its own not-configured failure instead of falling back. The CLI keeps its ephemeral empty-memory default and its warning. **Migration:** configure the registry through `data_registry=` or `BLUE_DATA_REGISTRY_STORE` / `BLUE_DATA_SOURCES_CONFIG`; see [deployment setup](docs/mcp.md#deployment-data-registry).
- **Breaking: the inert `timeout: 300` property seed is gone.** It no longer appears in `get_properties()`. Only a finite positive `execution.timeout_seconds` bounds how long `run()` waits; the deadline stops waiting but does not stop the worker or roll back its effects. **Migration:** set `execution.timeout_seconds` on calls that need a deadline.
- **MCP registry calls are serialized per server, and a timeout no longer needs a restart.** Initial registry construction runs outside the deadline. When `execution.timeout_seconds` expires, the caller gets `OPERATOR_TIMEOUT` at once while the timed-out worker keeps the server's registry lane; queued and new registry calls wait until it finishes and then run normally. Workers are not cancelled or rolled back, and one that never finishes keeps the lane. **Migration:** set backend and provider timeouts so a worker cannot hang, and expect a registry call to wait behind a timed-out one.
- **`data_discover` no longer returns stored connection details.** Earlier releases returned source `properties` and could expose credentials to any discovery caller. Results now contain `type`, `name`, `id`, `scope`, an optional `score`, and an allowlisted `properties.kind` for sources. `include_metadata=True` is refused. Stored connection settings, descriptions, and column metadata are omitted rather than redacted in place. **Migration:** consumers needing those details must read the registry through an appropriately authorized path.
- **The MCP handshake reports this package's version.** `serverInfo.version` was the protocol SDK's, because `FastMCP` takes no version argument and reports its own when it has none. It is now `1.0.0`, matching the declared `blue-data-ops-mcp` distribution version, so a client that cannot read distribution metadata can tell two adapter releases apart. The server also sends an `instructions` string, which was `None`.
- **The MCP service directory is `platform/ops-mcp/`.** It was `platform/mcp/`. A service directory under `platform/` is named for its family and its service, which is what the new `platform/ops-cli/` is named for too. The distribution name `blue-data-ops-mcp` and the import name `blue_data_ops_mcp` are unchanged, so nothing a caller installs or imports moved.
- **Both adapters now pin core 1.0.0 exactly; the CLI also requests its `ml,vector,llm` extras.** The pin is exact by design: the tool schemas are a projection of core's attribute specs. Update the pair together.
- **`.gitignore` ignores `*.envrc` rather than `.envrc` alone, and `.venv` as well as `.venv/`.** The bare name matched one file, and the trailing-slash pattern matched a directory but not a symlink of that name pointing at an environment elsewhere.
- **The design and user documentation record the three-distribution shape.** Every offline example has its captured output checked in beside it.
