# Changelog

Notable changes per release, newest first.

This repository publishes three distributions and versions each independently, so an entry names which of them moved and what a caller of that one has to do.
The rules are in [design/12-deployment-ops.md](design/12-deployment-ops.md#1-versioning); an operator card's own `@MAJOR.MINOR.PATCH` is a fourth axis and moves with neither.

## blue-data-ops 3.1.0, blue-data-ops-mcp 1.0.0, blue-data-ops-cli 1.0.0 — released

A command line that did not exist, a renamed MCP tool surface, a published schema that finally says what the library enforces, and two security repairs on paths no document ever sanctioned.
One break a caller must act on — every MCP tool is renamed — and one contract tightening that a validating client will notice before the server does.
Core stays a minor release: it gains scripts, a licence, and the two repairs, and removes nothing.

**Added**

- **A command line, `blue-ops`, in a new distribution `blue-data-ops-cli`.** 24 commands over `profile`, `catalog`, `operator`, `pipeline` and `metadata`, with `operator resource` under `operator`, in the `<cli> <component> <action>` shape the rest of the Blue family uses. It runs an operator over a record bundle, searches and inspects the catalog, exports an operator's resource package, and plans, stores, inspects and runs pipelines. A record bundle arrives as a file or on standard input rather than as an argument, because `list[list[dict]]` does not survive argv. `--format table|json|nl` is on every command that returns a result, settings resolve through command option → environment variable → profile → built-in default, and ten exit codes carry the library's own failure families. [`docs/cli.md`](docs/cli.md) is the reference; [`platform/ops-cli/README.md`](platform/ops-cli/README.md) is its source of truth.
- **The MCP adapter installs a console command.** `blue-data-ops-mcp` replaces `python -c 'from blue_data_ops_mcp import serve; serve()'`, and `blue_data_ops_mcp.main` is the function behind it. The old Python call still works.
- **A `LICENSE` at the repository root**, covering all three distributions. There was none. It is a BSD 3-Clause licence with a fourth attribution and NOTICE clause, byte-identical to the copies the sibling source repositories carry.
- **`build.sh`, `install.sh` and `publish.sh` under each package's `scripts/`.** They wrap `python -m build`, `pip install -e` and `twine upload dist/*`, with this repository's sibling-checkout resolution of `blue-data` folded into the install path. Nothing runs them; they are the family's convention so a contributor moving between packages runs the same three commands.
- **This changelog, and `docs/cli.md`.** Release history previously lived only in the migration sections of the package READMEs.

**Changed**

- **Breaking: every MCP tool is renamed.** The 33 names gain an `ops_` prefix, so `select` becomes `ops_select` and `create_database` becomes `ops_create_database`. **Every existing client call site changes.** A client holds one flat tool namespace across the servers it has loaded, and this family ships a server per source: `create_database` was already served with a different meaning by `blue-data-user-source`, and both are writes. Nothing else about a tool moves — `_meta.operator_id` still carries the unprefixed logical name, the three arguments are the same containers, and the result envelope is unchanged. **Migration:** prefix the tool name at each call site. A client that reads its tool list from `list_tools()` rather than hardcoding names needs no change beyond a fresh listing.
- **The published MCP input schema now says what core already enforced, which is a contract break rather than a behaviour break.** Each attribute carries its JSON Schema `type`, an attribute core declares required appears in the `attributes` object's `required` list — 46 of them, across 27 tools — and 17 attributes whose values core's validator closes carry an `enum`. The three top-level arguments each carry a description. **The server's own behaviour is unchanged**: it does not validate against the published schema, so a call that omits a required attribute still reaches operator validation and comes back as a recoverable `INVALID_INPUT` record with `isError` false, exactly as before. What changes is what a *client* does with it: a client that validates arguments against the advertised schema will now refuse a call it used to send, and the server would still have answered. **Migration:** a caller that was relying on the schema's permissiveness to send a partial `attributes` object gets a client-side refusal; send the required attributes, or stop validating locally and read the error record the server returns.
- **Breaking: the provider is the deployment's, not the caller's.** A model name is a routing instruction to the provider library — `vertex_ai/gemini-2.5-pro` selects Vertex, and so does a bare `gemini-2.5-pro` — so a caller who could set `openai.model` could choose which provider spent this deployment's credentials. Dispatch now comes from the environment the process starts in, which is the one channel a tool caller cannot reach. `BLUE_DATA_LLM_PROVIDER` names the provider on every call and defaults to `openai`; it is checked against the provider library's own name list before each LLM-backed call, and a name the library does not serve is refused with `bad_provider`, naming the variable and the value. Where that library will not enumerate its providers there is nothing to check against and the call proceeds. `BLUE_DATA_LLM_ALLOWED_MODELS`, when set, is the exact model set a property may ask for, and it only ever narrows. A model that would dispatch elsewhere is refused with `model_not_allowed`, checked both on the outcome the provider library would produce and on the spelling, because neither check covers the other. A slash is not itself a provider prefix: `accounts/fireworks/models/llama-v3` names a model and is accepted without listing. **Migration:** a deployment reaching any provider other than OpenAI through the model string must set `BLUE_DATA_LLM_PROVIDER`. Until now the provider was inferred from the model name, so this worked by accident.
- **Breaking on an unsanctioned path: a prefixed property namespace is now a closed set.** Before this release, a `properties` entry naming any LiteLLM field — `api_key`, `api_base`, `base_url`, `custom_llm_provider`, `extra_headers`, the Vertex and Bedrock project, tenant and region selectors, and the rest — was merged into the provider call and forwarded. The namespace now admits the generation parameters of the call and refuses everything else, so which provider answers, at which endpoint, in which project, tenant or region, and under which credential are the deployment's to set and not a caller's. On the MCP adapter `properties` is a tool argument, so **any caller that could reach a tool could send that server's prompt to an endpoint of their choosing, authenticated with a key of their choosing, and the deployment had no sign of it**. Nothing in this repository ever documented that route; the endpoint and the credential come from the environment the server process starts in. Such a property now raises `LLMError` with code `reserved_field`, naming the fields it refused, before the cache key is built — so nothing sent under one of those names is written to the response cache either. A census of forbidden names would be right only until the provider library's next release, so the rule is the other way round: the namespace admits a closed set of generation parameters, derived from that library's own call signature and supported keyword surface, and refuses everything outside it. **Migration:** put the key and the endpoint in the environment the server or the process starts in. A deployment that discovered `openai.api_key` worked will now get an error result instead of an answer.
- **Breaking on the same kind of path: a substituted provider response is refused.** LiteLLM returns `mock_response` verbatim without calling anyone, so a `properties` entry setting it made a tool hand back text the caller wrote, presented as a model's answer. Over MCP the caller is usually one agent and the reader of the answer another, which makes that an integrity problem regardless of how far it travels. `mock_response` and `mock_timeout` now raise `LLMError` with code `reserved_field` and their own message. **Migration:** inject a client through `properties["llm_client"]` to serve canned responses in a test, which is the seam that exists for it.
- **`data_discover` masks stored connection secrets in its results.** A registered `blue-data` source keeps its connection settings in `properties`, and the SQL, graph and Redis sources default a `password` there while the Mongo source builds `protocol://username:password@host:port`. `data_discover` returned that map as it stood, so **until this release a stored password was readable by anyone who could call `data_discover`** — including, on the MCP adapter, any client holding the tool. Secret-shaped keys now read `***` and the userinfo half of a connection URI reads `***:***`. Everything a discovery result exists for — protocol, host, port, database, and the column metadata — is returned unchanged, and bare `key` is deliberately not masked because `misc` carries primary and foreign keys and hiding those would hide the shape of the data a caller came to find. The result's shape, key set and types do not change. The masking is wider than a key lookup. A name is matched however it is spelled — hyphenated, camel-case, dotted, spaced, percent-encoded or form-encoded — and an account name such as `user`, `username` or `uid` counts as half of a credential pair. It reaches inside any stored string, so a credential written as an assignment is masked in a query string, in an ODBC or JDBC connection string, and in a URI's userinfo. A source's **description** is redacted too, for the connections inside it: a description that reads `connect with postgresql://u:pw@h/db` used to return that credential to any caller. **Migration:** a consumer that was building a connection string out of `data_discover` output now finds masked values there and breaks, and should read the registry directly instead; discovery is a search surface.
- **The MCP handshake reports this package's version.** `serverInfo.version` was the protocol SDK's, because `FastMCP` takes no version argument and reports its own when it has none. It is now `1.0.0`, matching `blue-data-ops-mcp` on the index, so a client that cannot read distribution metadata can finally tell two adapter releases apart. The server also sends an `instructions` string, which was `None`.
- **The MCP service directory is `platform/ops-mcp/`.** It was `platform/mcp/`. A service directory under `platform/` is named for its family and its service, which is what the new `platform/ops-cli/` is named for too. The distribution name `blue-data-ops-mcp` and the import name `blue_data_ops_mcp` are unchanged, so nothing a caller installs or imports moved.
- **The adapter's core pin moves from `blue-data-ops==3.0.0` to `==3.1.0`, and the CLI pins the same release.** The pin is exact by design: the tool schemas are a projection of core's attribute specs. Update the pair together.
- **`.gitignore` ignores `*.envrc` rather than `.envrc` alone, and `.venv` as well as `.venv/`.** The bare name matched one file, and the trailing-slash pattern matched a directory but not a symlink of that name pointing at an environment elsewhere.
- **The design and user documentation record the three-distribution shape.** The sentences asserting that neither `pyproject.toml` declared `[project.scripts]`, that there were no shell scripts anywhere in the tree, and that `docs/` carried no CLI page are gone, because all three were true and are not. Every offline example now has its captured output checked in beside it.
